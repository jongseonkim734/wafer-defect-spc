# DMAIC 정합성 문서

> 이 프로젝트는 6시그마를 알기 전에 시작됐다. 그래서 **결과는 DMAIC와 상당 부분 겹치지만, 방법론을 의식하고 설계한 것은 아니다.**
> 이 문서는 (1) 이미 한 일을 DMAIC에 정직하게 매핑하고, (2) **비어 있는 칸을 명시**하고, (3) 그 칸을 무엇으로 채울지 계획한다.
>
> 원칙: **없는 것을 있는 척하지 않는다.** 빈 칸은 빈 칸으로 두고 채워 나간다. 면접에서 방어 가능한 문서를 만드는 것이 목적이다.
>
> 작성 시작: 2026-09-07 (6시그마 GB 취득일)

## D — Define

### 이미 있는 것
- 대상 문제 두 개: 공정 중 센서 이상 탐지(SECOM) / 공정 후 웨이퍼맵 불량 분류(WM-811K)
- 성공 기준의 방향: **소수 불량을 놓치지 않는 recall 우선** (FN이 FP보다 치명적이라는 품질 판단)
- 왜 중요한가: 수율·품질 직결

### 비어 있는 것
1. **CTQ가 명문화되어 있지 않다.** 지금은 "recall 우선"이라는 방향만 있고, *무엇이 CTQ이고 목표치가 얼마인지*가 문서에 없다.
   → 채울 것: CTQ를 **Scratch recall**과 **SECOM fail recall** 두 개로 명시하고, 각각 현 수준 / 목표 / 근거를 표로.
2. **SIPOC이 없다.** 이 프로젝트가 다루는 프로세스의 경계가 문서에 없다.
   → 채울 것: 전공정 → EDS → 웨이퍼맵 생성까지를 SIPOC 한 장으로. Customer는 후공정·품질 부서.
3. **목표수준의 근거가 없다.** "recall을 높인다"는 있지만 *얼마까지, 왜 그만큼*이 없다.
   → 채울 것: 벤치마킹(문헌의 WM-811K SOTA) 또는 비즈니스 기준(불량 1장 유출 비용)으로 목표 설정 논리를 붙인다.

> **왜 이게 비었나 (정직한 기록)**: 데이터를 먼저 만지고 문제를 나중에 좁혔다. Define을 건너뛴 대가로 Improve에서 방향 없이 세 번 실패했다 — 이 인과 자체가 회고 자산이다.

## M — Measure

### 이미 있는 것
- **관리도**: X-bar / R 직접 구현 (`src/spc.py`, 단위 테스트 포함)
- **공정능력**: Cp / Cpk 구현
- **현 수준 측정**: SECOM baseline fail recall 0.19, WM-811K macro F1 0.842 / Scratch recall 0.57
- 결측 처리(median imputation), 불균형 처리(class_weight)

### 비어 있는 것
1. **MSA가 전혀 없다.** ← 가장 큰 구멍
   지금까지 *"모델이 맞았나 틀렸나"* 만 봤고, **측정 도구 자체가 믿을 만한가**는 검증한 적이 없다.
   → 채울 것 (**B안**):
   - **반복성(Repeatability)**: 같은 웨이퍼맵을 회전·반전해 반복 투입 → 같은 판정이 나오는가
   - **재현성(Reproducibility)**: seed를 바꿔 학습한 모델들 간 판정이 일치하는가
   - **Attribute Agreement Analysis**: 모델 판정 ↔ 실제 라벨의 일치도를 **Kappa**로
   - 클래스별로 분해 → *"Scratch에서만 측정 시스템이 흔들린다"* 를 정량화
2. **시그마 수준으로 환산한 적이 없다.**
   → 채울 것: SECOM 불량률(≈6.6%)과 WM-811K 오분류율을 **DPMO → 시그마 수준**으로 변환. 6시그마 언어로 현 수준을 말할 수 있게 된다.

> **왜 MSA가 중요한가**: 계측·측정을 업으로 하는 직무에서는 "측정 도구를 먼저 검증했다"는 사실 자체가 결과의 신뢰도를 좌우한다. 공정·양산 직무에서도 Gage R&R은 기본 언어다.

## A — Analyze

### 이미 있는 것
- **ANOVA F-검정**으로 590개 중 유효 인자 선별 (k-sweep으로 k=10 최적)
- **Grad-CAM**으로 오분류의 판단 근거 시각화 → "모델은 옳은 곳을 보되 선을 덩어리로 읽는다"
- **z-score 기반 원인 인자 순위화** (정상 Lot 기준선 대비 이탈도)
- **연결요소 분리 + 종횡비**로 Scratch/Loc 분리 (5.78 vs 1.86, IQR 완전 분리)
- 인자가 **그룹으로 움직인다**는 발견 (센서 430·431·434·435 동반 이탈, 400 포화)

### 비어 있는 것
1. **특성요인도(5M1E)가 없다.**
   README에 이미 *불량 패턴 → 전공정 원인* 매핑 표가 있으니 **재료는 갖춰져 있다.** 이를 어골도로 재구성하면 원인 후보가 구조화된다.
   → 채울 것 (**E안**): 8종 불량 각각에 대해 Man/Machine/Material/Method/Measurement/Environment로 원인 가지치기. 여기에 FMEA(심각도·발생도·검출도 → RPN)로 우선순위.
2. **가설검정이 정식으로 서술되어 있지 않다.**
   ANOVA를 *썼지만* H0/H1을 세우고 유의수준을 정하고 p-value로 판정하는 형식이 문서에 없다.
   → 채울 것: 기존 분석에 귀무·대립가설과 판정 근거를 명시. 코드는 그대로, 서술만 6시그마 형식으로.
3. **회귀분석이 없다.** Y 연속형 × X 연속형 조합을 다룬 적이 없다.
   → 채울 것(선택): 센서값 → 불량 확률의 로지스틱 회귀는 이미 있으니, 계수 해석을 인자 영향도로 재서술.

## I — Improve

### 이미 있는 것
- **동일 조건 A/B 실험 3종**: 회전·반전 증강 / 해상도 64→96 / 고전 도메인 피처
- 세 실패의 공통점을 재검토해 **원본 해상도 연결요소 분석**으로 결론 반전
- 부수 발견: val_loss ↔ val_accuracy 불일치로 EarlyStopping이 undertrain 모델을 복원하는 문제 → monitor 교정

### 비어 있는 것
1. **실험이 DOE가 아니라 일요인 실험(OFAT)이었다.** ← 방법론적으로 가장 아픈 지점
   증강·해상도·피처를 **하나씩 따로** 바꿨다. 그래서 **교호작용을 볼 수 없었다.**
   → 채울 것 (**C안**): 2³ 요인배치로 재설계
   ```
   A: 입력 해상도   (64 / 96)
   B: 증강          (없음 / 회전·반전)
   C: class_weight  (uniform / balanced)
   → 8회 학습 → 주효과 + 2인자 교호작용 → 파레토 차트로 Vital Few 식별
   ```
   기대 결과: 세 인자 모두 주효과가 유의하지 않고, **진짜 인자는 실험 범위 밖(파이프라인 앞단)** 이었음을 통계로 보인다. 지금의 "돌려보니 안 됐다"가 **"설계된 실험으로 인자 없음을 확인했다"** 로 바뀐다.
2. **개선안 우선순위 도구가 없다.** 여러 처방 중 무엇을 먼저 할지 판단 근거가 없었다.
   → 채울 것: Payoff Matrix(효과 × 난이도) 한 장.

> **정직하게 남길 것**: DOE를 지금 하는 이유는 결과를 바꾸기 위해서가 아니다. 결론(리사이즈가 원인)은 이미 맞다. **같은 결론에 도달하는 더 나은 경로**가 있었음을 보이는 것이 목적이다.

## C — Control

### 이미 있는 것
- 없음. (devlog에 회고는 있으나 관리 체계는 아니다)

### 비어 있는 것 — 전부
1. **관리계획서(Control Plan)**: 관리항목 / 규격 / 측정방법 / 주기 / 담당 / 이상 시 조치를 표 한 장으로.
2. **모델 성능 관리도**: 배치별 macro F1에 관리한계선을 설정하고, 이탈 시 재학습 트리거. **SPC를 모델 자체에 적용**하는 것이라 이 프로젝트의 두 축(SPC · ML)이 여기서 만난다.
3. **표준화·수평전개**: 파이프라인을 재현 가능한 형태로 문서화. WM-811K에서 얻은 "리사이즈 전 형태 정보를 보존하라"는 교훈을 다른 데이터셋에 적용 가능한 원칙으로.

→ **D안**

## 작업 순서 (제안)

```
1) A안 — 이 문서 (완료)             ← 지금 여기. 빈 칸이 어디인지 확정
2) E안 — 특성요인도 + FMEA          ← 반나절. 코드 없이 문서만, 몸풀기
3) B안 — MSA (반복성·재현성·Kappa)  ← 1~2일. 계측·분석 직무를 겨냥할 때 최우선
4) C안 — DOE 2³ 요인배치            ← 2~3일. 학습 8회라 가장 오래 걸림
5) D안 — Control Plan + 성능 관리도 ← 1일. 마지막에 전체를 묶음
6) README·devlog를 DMAIC로 재구성   ← 위 결과를 반영해 최종 정리
```

> C안(DOE)은 학습 8회라 시간이 제일 걸리므로, **착수는 빠를수록 좋다.** 돌려두고 다른 작업을 병행할 수 있다.

## 면접 대응 (이 문서의 최종 용도)

> **Q. 6시그마 GB 있으시네요. 그런데 자격증만 있고 실제로 써보신 적은 없죠?**

**A.** 개인 프로젝트에 적용했습니다. 다만 순서가 거꾸로였습니다 — 프로젝트를 먼저 하고, 나중에 6시그마를 배우면서 제가 뭘 빠뜨렸는지 알게 됐습니다.

가장 크게 걸린 건 **Improve 단계**였습니다. 웨이퍼 불량 분류에서 특정 클래스 성능이 낮아 세 가지 개선을 시도했는데, 전부 **인자를 하나씩만 바꾸는 방식**이었습니다. 셋 다 실패했고, 그때는 "데이터의 한계"라고 결론지었습니다. 나중에 요인배치로 다시 설계해보니 **세 인자 모두 주효과가 유의하지 않았고**, 진짜 원인은 제가 실험 대상으로 삼지도 않았던 **파이프라인 맨 앞의 리사이즈 결정**이었습니다.

그리고 **Measure 단계**에서 측정 시스템 자체를 검증한 적이 없다는 것도 알았습니다. 그래서 분류 모델을 하나의 측정 도구로 보고 **반복성과 재현성**을 나눠 측정했고, 클래스별 일치도를 Kappa로 확인했습니다.

**배운 건 이겁니다** — 모델을 의심하기 전에 측정을 의심하고, 인자를 하나씩 바꾸기 전에 실험을 설계해야 한다는 것입니다.
